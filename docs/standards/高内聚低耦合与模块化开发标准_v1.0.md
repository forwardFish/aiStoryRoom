# Our Many Worlds 高内聚、低耦合与模块化开发标准 v1.0

## 1. 目的

本标准把“高内聚、低耦合、分模块”定义为强制开发方式，而不是文档排版或项目
计划形式。目标是让每次改动都具备以下特征：

- 问题能够快速定位到唯一模块；
- 模块能够独立修改、测试、回滚和验收；
- 已经正确的模块不会被无关改动反复破坏；
- 新需求不会产生第二权威、平行运行时或跨层规则复制；
- 玩家能够在每个可见模块完成后立即参与测试。

## 2. 核心定义

### 2.1 高内聚

一个模块只负责一类紧密相关的能力。该能力所需的规则、校验和测试应集中在该
模块内。

例如：

- Settlement 只负责裁定真实结果；
- Narrative Context Compiler 只负责选择并组织 Viewer-safe 叙事材料；
- Narrator 只负责表达已经允许的事实；
- Truth Guard 只负责校验 Narrative 是否越权；
- `/game` 页面只负责展示投影和收集玩家输入。

### 2.2 低耦合

模块之间只通过明确、最小、稳定的输入输出合同通信。一个模块不得依赖另一个
模块的内部实现，也不得跨层读取内部状态。

允许：

```text
SettlementResult
    -> Audience-safe Projection
    -> NarrativeContext
    -> NarrativeArtifact
    -> GameProjection
```

禁止：

```text
页面直接读取 Settlement 内部 WorkingDelta
Narrator 直接写数据库或改变结算结果
数据库适配器重新判断游戏规则
多个模块分别维护同一角色、资源或剧情事实
```

### 2.3 模块化开发

模块化开发要求代码边界、数据边界、测试边界、故障边界和验收边界同时成立。
仅仅把计划写成“第一阶段、第二阶段”不属于模块化。

## 3. 强制依赖方向

正常依赖方向为：

```text
内容与配置
    ↓
领域规则与权威裁定
    ↓
应用编排
    ↓
安全投影与适配器
    ↓
Provider 表达
    ↓
事实与输出校验
    ↓
API 投影
    ↓
玩家页面
```

规则：

- 下层可以接收上层产物，但不得反向改变上层权威；
- 页面不得实现领域裁定；
- Provider 不得产生权威事实；
- 持久化不得决定业务结果；
- 内容配置不得直接操作数据库或页面；
- 一个跨层需求必须通过适配器或窄合同连接，不得直接穿透。

## 4. 开发前必须提交模块卡

每个准备实施的模块必须先填写以下内容：

```text
模块名称：
用户目标：
唯一职责：
明确不负责：
输入及其权威来源：
输出及其消费者：
允许依赖：
禁止依赖：
准确生产文件：
准确测试文件：
修改前行为：
修改后行为：
失败归属：
聚焦测试：
真实验收方式：
玩家参与节点：
回滚方式：
```

缺少任何一项时，不得用“实现中再看”代替边界设计。

## 5. 实施门

### Gate 0：基线与归属

- 确认当前分支和工作树；
- 区分本任务、其他任务和用户已有改动；
- 保存修改前的真实行为证据；
- 确认本模块的准确文件所有权；
- 确认没有隐含的公共合同、数据库或页面变化。

### Gate 1：单模块实现

- 只修改模块卡批准的文件；
- 不顺手重构相邻模块；
- 不用临时旁路、重复规则或页面补丁掩盖后端问题；
- 模块输出尽量使用只读、不可变、可序列化的数据。

### Gate 2：模块聚焦验证

- 正常路径测试；
- 非法输入和越权路径测试；
- 与相邻模块的合同测试；
- 旧行为回归测试；
- 记录输入摘要、输出摘要和准确错误归属。

### Gate 3：真实流程验收

- 玩家可见能力必须进入真实批准路由；
- 项目所有者在真实流程中参与测试；
- 当前模块未认可前，不进入后续模块；
- 不得用自动化测试代替剧情质量、交互质量或视觉质量验收。

### Gate 4：受控保留

- 列出模块准确修改文件；
- 说明每个文件为什么属于该模块；
- 列出明确未修改的系统；
- 更新必要版本与哈希，禁止相同版本对应不同正式内容；
- 未获授权不提交、不推送、不部署。

## 6. 故障定位标准

出现问题时，必须先归类，再修改：

| 故障表现 | 首要归属模块 | 禁止的错误处理 |
|---|---|---|
| 原始剧情材料错误 | 内容/Story Package | 在页面硬编码补文案 |
| 角色知道不该知道的事 | Audience Projector | 用 Prompt 请求模型“忽略” |
| 六席结果不正确 | Settlement | 修改 Narrative 掩盖结果 |
| 事实正确但材料缺失 | Context Compiler | 让 Provider 自行猜测 |
| 人物口吻或节奏不好 | Narrator Prompt | 修改 Settlement 或数据库 |
| Narrative 捏造事实 | Truth Guard/Prompt | 只换同义词继续发布 |
| API 正确但页面没显示 | Projection/UI Adapter | 新建平行页面 |
| 页面布局意外变化 | UI | 顺手重新设计正式页面 |

连续两次修复没有改善时，必须重新验证故障归属，不得继续在同一层堆补丁。

## 7. 模块测试标准

每个模块至少需要：

1. 一个正常路径聚焦测试；
2. 一个非法输入或越权测试；
3. 一个旧行为回归测试；
4. 一个模块边界合同测试；
5. 玩家可见模块对应的真实页面证据。

测试应验证模块公开行为，不应依赖内部偶然实现。不得为了让测试通过而放宽权威、
隐私、安全或版本约束。

## 8. 变更规模与重新审批条件

出现以下任一情况必须停止并重新提交模块说明：

- 需要修改模块卡之外的生产文件；
- 需要新增或修改公共合同；
- 需要新增数据库表、migration、路由或页面；
- 需要改变 Settlement、权限或唯一事实来源；
- 一个修复必须同时穿透三个以上既有模块；
- 出现第二套状态、第二套规则或第二条真实玩家运行路径；
- 无法为失败提供唯一首要归属。

## 9. 禁止模式

- “万能” Manager、Service、Helper 或 Utils 同时承担多个领域职责；
- 页面、API、Prompt、数据库分别复制一份相同规则；
- 共享可变全局状态作为模块通信方式；
- 为绕开现有合同建立平行运行时；
- 把调试字段、内部错误码和证据 ID 暴露给玩家；
- 一个大改完成后才一次性测试全部功能；
- 当前模块失败时继续开发后续模块；
- 用“测试通过”代替真实玩家体验验收。

## 10. Pressure 剧情与决策的标准模块链

Pressure 相关开发默认按以下模块定位：

```text
Story Source
    ↓
Decision Presentation
    ↓
Player/AI Action Policy
    ↓
Six-seat Settlement
    ↓
Audience-safe Narrative Source
    ↓
Narrative Context Compiler
    ↓
Narrator Provider
    ↓
Truth Guard
    ↓
Game Projection Adapter
    ↓
Frozen /game UI
```

任何“剧情不好”或“决策不好”的问题，都必须先定位到这条链中的一个首要模块，
再进行修改。不得默认归因于模型，也不得跨越多个模块同时试错。

## 11. 完成交付格式

每次交付必须逐模块报告：

```text
模块：
修改文件：
解决的问题：
修改后的行为：
明确未改范围：
聚焦测试结果：
真实流程结果：
已知问题：
回滚点：
```

只有所有批准模块分别通过，并且真实端到端用户流程也通过，才能声明整体完成。
